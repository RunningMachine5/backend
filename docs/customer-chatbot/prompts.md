# 고객 대응 챗봇 — LLM 프롬프트

[고객 대응 챗봇 설계 (PRD)](README.md)의 부속 문서다.
챗봇이 LLM에 보내는 프롬프트 전문을 모아둔다.
흐름과 분기 조건은 PRD의 [2. 작동 시나리오](README.md#2-작동-시나리오)에 있다.

고객에게 출력하는 안내 문구는 이 문서가 아니라
[고객 안내 문구](messages.md)에 있다.

| 절 | 프롬프트 | 사용처 |
| --- | --- | --- |
| [A.1](#a1-고객응답-평가-프롬프트) | 고객응답 통합 분석 | 응답 판정 3종 + 검색 질의 최대 5개 |
| [A.2](#a2-가이드-검색-질의-분해-프롬프트) | 가이드 검색 질의 규칙 | A.1 통합 분석의 targeted query 생성 규칙 |
| [A.3](#a3-사기-정황-추출-프롬프트) | 사기 정황 추출 | `fraud_circumstance` 20종 |
| [A.4](#a4-대응-가이드-생성-프롬프트) | 대응 가이드 생성 | RAG Generate 1회 통합 호출 |

> 사기 정황의 `type` 허용값은 프롬프트가 아니라 파이썬 코드로 강제한다.
> PRD [DB·스키마 3.8](schema.md#38-appdomain-enum-코드-상수화)를 따른다.

#### 프롬프트에 적용한 출력 원칙

통합 분석(A.1, A.2 규칙 포함)·사기 정황 추출(A.3)은
[build_structured_llm](../../app/services/chatbot/llm.py)의 `strict=True` `json_schema`를 쓴다.
두 구조화 출력 호출은 스키마가 강제하는 출력 형식·enum 화이트리스트를 프롬프트에 중복하지 않는다.

대응 가이드(A.4)는 고객에게 보이는 본문을 토큰 조각부터 전달해야 하므로 예외다. 일반 텍스트
스트림을 사용하고, `■ 소제목`·입력 순서·B.5 문구·JSON 금지를 프롬프트가 정한다. A.4에는
별도 Pydantic 출력 DTO나 위치별 후처리 파서가 없다.

| 뺀 것 | 어디에 있었나 | 대신 보장하는 것 |
| --- | --- | --- |
| `출력 형식: { ... }` JSON 예시 블록 | A.2 · A.3 | 각 Pydantic 응답 스키마가 그대로 전송된다. 필드의 의미는 규칙 목록이 설명한다 |
| `출력은 JSON만 반환하세요` | A.1 | `json_schema` 구조화 출력 |
| `JSON 이외의 설명이나 마크다운을 출력하지 않습니다` | A.2 | 같음. A.3에는 아직 남아 있다 |
| `허용된 enum 이외의 값은 생성하지 않습니다` | A.3 | `Literal[*FINAL_FRAUD_CIRCUMSTANCE_CODES]` + 저장 직전 검증([스키마 3.8](schema.md#38-appdomain-enum-코드-상수화)) |

**컨텍스트에 없는 정보는 금지하지 않는다.** A.1과 그 안의 A.2 규칙은 직전 질문과 고객 답변을
함께 받고, A.3은 고객 답변만 받는다([3.2](README.md#32-프롬프트rag)). 프롬프트에 들어오지
않는 입력이나 도달하지 않는 입력을 금지하는 규칙은 판단 공간만 넓힌다.

| 뺀 규칙 | 왜 |
| --- | --- |
| `침묵/무응답은 이 노드에 들어오지 않으므로 고려하지 않습니다` (A.1) | `_evaluate` 노드는 고객 메시지가 있을 때만 실행된다. 없는 분류지를 상기시킬 뿐이다 |
| `사기유형을 먼저 결정한 뒤 그 유형에 맞춰 정황을 생성하지 않습니다` (A.3) | 프롬프트에 사기유형이 없다. `top_fraud_types`는 [질문 렌더링](../../app/services/chatbot/questions.py)에만 쓴다 |
| `후보 사기유형이나 거래 정보만으로 정황을 생성하지 않습니다` (A.3) | 같음. 거래 정보도 프롬프트에 넣지 않는다 |

### A.1 고객응답 평가 프롬프트

사용처: [2.4 조건 2](README.md#조건-2-고객응답-평가-llm)

운영 파이프라인은 이 판정과 A.2의 가이드 검색 질의 분해를
`AnswerAnalysisResult { verdict, guide_search_queries }` 한 번의 구조화 출력으로 받는다.
`TOO_VAGUE`와 `WANT_END`는 `guide_search_queries=[]`를 강제하고, `SUFFICIENT`만 아래
A.2 규칙으로 0~5개의 targeted query를 함께 만든다.

```text
ANSWER_ANALYSIS_PROMPT = """
당신은 금융 이상거래 상담 챗봇에서 고객 응답을 한 번에 분석합니다.

직전 질문: {question_text}
고객 응답: {customer_answer}

먼저 다음 중 하나로 verdict를 분류하세요.

- SUFFICIENT: 질문 목적에 맞는 구체적 사실이 확인됨
- TOO_VAGUE: 질문 목적에 필요한 정보를 확인할 수 없는 응답
- WANT_END: 상담을 종료하기를 원함

규칙:

- 모호하거나 질문과 무관한 답변, "모름"·"기억 안 남" 같은 판단 불가 응답은 TOO_VAGUE로 분류합니다.
- 현재 질문에 대한 답변만 거부하거나 회피하는 경우와 고객이 되묻는 경우도 TOO_VAGUE로 분류합니다.
- 전체 상담을 그만두거나 종료하겠다는 의사가 명확한 경우에만 WANT_END로 분류합니다.
- verdict가 TOO_VAGUE 또는 WANT_END이면 guide_search_queries는 반드시 빈 배열입니다.
- verdict가 SUFFICIENT이면 A.2 규칙에 따라 가이드 검색 질의를 함께 생성합니다.
"""
```

### A.2 가이드 검색 질의 분해 프롬프트

사용처: [2.5 가이드 검색 질의 분해](README.md#가이드-검색-질의-분해)

아래 규칙은 별도 템플릿이 아니라 A.1 통합 프롬프트의
`GUIDE_SEARCH_QUERY_RULES` 부분이다. 운영 고객 턴과 RAGAS 골든셋 평가가 모두
`AnswerAnalyzer`를 호출하므로 판정과 질의 분해 계약이 같다.

```text
당신은 금융 이상거래 상담에서 고객 답변을 RAG로 독립 검색할 수 있는 가이드 검색 질의로 분해합니다.

다음 규칙을 따르세요.

- 금융사기 대응에 의미 있는 행동, 정보 노출, 상대방과의 접촉을 가이드 검색 질의로 변환합니다.
- 그런 행동이 없더라도 계좌·카드·이체·결제·대출·금융 보안 서비스처럼 금융과 관련된 질문이나 걱정이 있으면 가이드 검색 질의로 변환합니다.
- 금융과 무관한 배경 사실만 있으면 가이드 검색 질의로 만들지 않습니다.
- 각 가이드 검색 질의는 다른 대화 문맥 없이도 검색 가능한 완결된 한국어 질의여야 합니다.
- 한 가이드 검색 질의에는 하나의 대응 주제만 포함하고, 서로 독립적으로 검색할 수 있게 분리합니다.
- 고객이 실제로 묻거나 말한 것만 질의로 만듭니다. 신청 방법·조건·자격·절차처럼 고객이 묻지 않은 하위 항목을 새로 덧붙이지 않습니다.
- 한 질의는 물음 하나로 씁니다. 두 물음을 한 문장에 이어 붙이지 않습니다.
- 같은 의미의 요구를 중복하거나 겹쳐 만들지 않습니다.
- 5개는 상한일 뿐 목표가 아닙니다. 답변에서 실제로 확인되는 것만 만들고, 개수를 채우려고 일반적인 신고·증거보존·절차 안내를 덧붙이지 않습니다.
- 대응할 가이드 검색 질의가 하나뿐이면 하나만, 없으면 빈 배열을 반환합니다.
- title은 고객에게 보여줄 간결한 한국어 소제목입니다.
- search_query는 대응 가이드 문서를 찾기 위한 한국어 질문이며, 고객이 말한 범위를 벗어나지 않습니다.
- evidence는 그 질의의 근거가 된 사용자 답변 부분입니다.

사용자 답변:
{{user_answers}}
```

#### 규칙을 줄인 이유

A.2는 최대 5개 객체 × 자유 텍스트 3필드를 만드는 작업이라 과거 분리 측정에서 네 LLM 호출 중
가장 느렸다. 현재 운영 경로는 A.1과 A.2를 합쳤다. A.3은 enum 선택이고, A.4는 근거가 있는 검색 질의를
한 번에 안내문으로 만든다. A.2의 규칙이 많을수록 열린 출력 공간에서 검사할 것이 늘어
추론 토큰까지 함께 커진다
(모델별 측정값은 [PRD 2.4](README.md#모델reasoning-effort와-타임아웃-예산)).

**형식 제약의 최종 강제는 구조화 출력 스키마가 맡는다.**
`strict=True`의 `json_schema`는 `maxItems`/`maxLength`를 제약 디코딩으로 강제한다(8개·30자를
요구해도 스키마대로 2개·10자로 제한되는 것을 확인했다). 프롬프트에는 숫자 검증 규칙을
중복하지 않고, 5개를 목표치로 채우지 말라는 생성 의도만 적는다.

| 뺀 규칙 | 대신 보장하는 것 |
| --- | --- |
| 최대 5개만 반환 | `AnswerAnalysisResult.guide_search_queries`의 `max_length=5`. 프롬프트에는 **5개는 상한일 뿐 목표가 아니다**라는 생성 의도를 남긴다 |
| title 120자 / search_query 500자 | `ExtractedGuideSearchQuery`의 `Field(max_length=...)` ([app/dto/chatbot.py](../../app/dto/chatbot.py)) |

`evidence`의 출력 예시는 현재 코드와 같이 `사용자 답변의 정확한 원문`이라고 쓰지만,
규칙 목록에는 연속 원문 제약이 없다. 추출 서비스는 원문과 다른 `evidence`가 와도 질의를
RAG로 넘기고, 리포지토리는 원문에 포함되지 않은 `evidence`의 감사 행만 저장하지 않는다.

**개수 제한을 상한으로 다시 쓴 이유**는 모델이 「최대 5개」를 목표치로 읽었기 때문이다.
행동이 하나뿐인 답변(「입금받은 돈을 다른 계좌나 사람에게 다시 송금했어」)에서도 5개를
채워, 「거래 내역 보존 및 증거 확보 절차」처럼 답변에 없는 일반 절차나 은행 내부 절차가
섞였다. 스키마가 상한을 강제하므로 프롬프트가 할 일은 **채우지 않게 하는 것**뿐이다.

**함께 뺀 서술 규칙 2종**은 형식이 아니라 판단을 요구해 추론 비용이 큰 쪽이었다.

- `사용자가 언급한 순서를 유지` — 고객이 말한 순서와 안내 순서가 달라질 수 있다. 다만
  응답 조립의 위치 번호는 코드가 `enumerate`로 매기므로 0건 폴백(B.5)을 포함한 모든 요구가
  빠짐없이 나타나는 것은 그대로다([2.5](README.md#검색-결과-0건-처리)).
- `부정한 행동·요청만 받은 행동 제외` — **환각 가드였다.** 「링크는 안 눌렀어요」에서
  링크 클릭 대응 가이드가 나올 수 있다. [3. 미해결 문제](README.md#3-미해결-문제)에
  관찰 대상으로 남긴다.

#### 금융 일반 질문까지 넓힌 이유

원래 첫 규칙은 **금융사기 대응에 의미 있는 행동·정보 노출·접촉**만 질의로 바꾸게 했고,
둘째 규칙(`단순 배경 사실은 답변 안에서 사기 위험과 연결된 경우에만 포함`)이 그 밖을 막았다.
그래서 고객이 사기 행동을 서술하지 않고 제도만 물으면 — 「오픈뱅킹 안심차단에 가입하면
무엇이 차단되나요?」 — 질의가 **빈 배열**로 나오고 응답이 통째로 비었다.

이 상태는 두 곳에서 문제가 됐다.

- **고객 응대**: 사기 정황이 아직 없는 예방·제도 문의에 아무 안내도 못 준다. 코퍼스에는
  그 답이 들어 있는데도 검색 자체가 시작되지 않는다.
- **RAG 평가**: 골든셋의 제도 문의형 사례가 검색 0건 → 응답 없음으로 떨어져 채점 지표가
  0이 된다([evals/rag/README.md](../../evals/rag/README.md)의 「질문 말투」 절).

그래서 막던 둘째 규칙을 빼고 **금융 관련이면 질의를 만든다**로 넓혔다. 대신 빈 배열 조건이
사라지지 않도록 `금융과 무관한 배경 사실만 있으면 만들지 않는다`를 남겼다 — 「점심 뭐
먹었는지」류는 그대로 걸러진다.

넓힌 만큼 **0건 비율은 오히려 올라갈 수 있다.** 전에는 만들지 않던 질의가 생기고, 코퍼스가
그 주제를 덮지 못하면 [2.5의 0건 분기](README.md#검색-결과-0건-처리)로 B.5 문구가 나간다.
안내를 못 주는 것은 같지만, "왜 못 주는가"가 **질의 미생성**에서 **코퍼스 커버리지**로
옮겨가 [3. 미해결 문제](README.md#3-미해결-문제)의 코퍼스 과제로 측정·개선할 수 있게 된다.

#### 고객이 묻지 않은 하위 항목을 막은 이유

`완결된 한국어 질의`와 `구체적인 한국어 질문`은 자립성만 요구했지 **범위**를 정하지 않았다.
그래서 모델이 고객 발언에 없는 빈칸을 상상으로 채웠다.

RAG 평가 `easy-011`(「오픈뱅킹 안심차단은 누구나 가입할 수 있나요? 미성년자인 자녀 계좌도
걸어두고 싶은데요」)에서 두 번째 질의가 「미성년자인 자녀 명의 계좌에도 오픈뱅킹 안심차단을
신청할 수 있나요? **법정대리인의 신청 방법과 조건은 무엇인가요?**」로 나왔다. 고객은 법정대리인을
묻지 않았다. 그 결과:

- 질의 1은 `F07 p8/p6/p2`를 검색했다 — 정답 근거(만 19세 이상, 미성년자 불가)가 여기 있다.
- 질의 2는 `P02 p44/p43`, `F04 p4`를 검색했다 — 지어낸 어절이 임베딩을 다른 문서로 끌고 갔다.
- A.4의 `근거에 없는 절차를 만들어내지 않는다`가 정상 작동했고, 질의 2의 검색 근거가 없어
  [B.5](messages.md) 폴백 섹션이 응답에 붙었다.

응답이 필요한 사실은 이미 다 말했는데 「자료를 찾지 못했어요」 블록이 덧붙어 RAGAS
`factual_correctness`가 깎였다. **환각 답변이 아니라 지어낸 하위 질의가 만든 잉여 폴백**이
원인이다. 아이러니하게도 `F07 p8` 원문에는 법정대리인 대리 신청 내용까지 들어 있는데,
질의 2가 그 페이지를 뽑지 못해 쓰지 못했다.

`가입 대상과 신청 자격은 어떻게 되나요?`처럼 한 질의에 물음 둘을 이어 붙인 것도 같은 사례에서
나왔다. `하나의 대응 주제만` 규칙이 주제 수만 말하고 문장 형태를 말하지 않아, 임베딩이
두 물음 사이에서 희석된다.

그래서 규칙 두 줄을 넣고 `search_query`의 `구체적인`을 뺐다.

- `고객이 실제로 묻거나 말한 것만 질의로 만듭니다. 신청 방법·조건·자격·절차처럼 고객이 묻지 않은 하위 항목을 새로 덧붙이지 않습니다.`
- `한 질의는 물음 하나로 씁니다. 두 물음을 한 문장에 이어 붙이지 않습니다.`

[규칙을 줄인 이유](#규칙을-줄인-이유)의 지연 우려와 상충하지 않는다. 이 둘은 A.1·A.3 같은
판단형이 아니라 **억제형**이라 출력 공간을 넓히지 않는다. 뺐던 서술 규칙 2종보다 추론 비용이
작을 것으로 보고 넣었으며, 실제 지연은 재측정으로 확인한다.

**하지 않은 대안 두 가지**를 남긴다.

- `MAX_DISTANCE = 0.6` 완화 — 지어낸 질의에도 아무 청크나 붙어 `faithfulness`가 함께 떨어진다.
- [extractors.py](../../app/services/chatbot/extractors.py)에서 `search_query` 후처리 검증 —
  의미적 창작은 원문 부분문자열 검사로 잡히지 않는다.


### A.3 사기 정황 추출 프롬프트

사용처: [2.6 사기 정황 추출과 채점](README.md#26-사기-정황-추출과-채점-4-2) · `fraud_circumstance` 20종

판정 원칙:

- 사용자 답변 전체를 읽고, 같은 사건을 설명하는 여러 문장이나 절에 나뉜 정보를 함께 판단합니다.

- 정의가 상대방의 요청이나 주장 자체를 정황으로 삼으면 사용자가 그 요청을 수행하지 않았어도 추출합니다.
- 하나의 답변에서 여러 정황이 확인되면 빠뜨리지 말고 각각 추출합니다.
- 정황들은 서로 배타적이지 않습니다. 더 구체적인 정황을 추출했더라도 그 전제가 다른 정의에도 해당하면 둘 다 추출합니다. 특히 가족·지인 사칭과 휴대폰 고장 설명·제3자 계좌 송금 요청·상품권 정보 요청은 함께 추출할 수 있습니다.
- urgent_transfer_to_third_party_account 또는 gift_card_pin_requested_by_impersonated_contact을 추출하면, 두 정의에 가족·지인 사칭이 필수로 포함되므로 family_or_friend_impersonated_in_messenger도 함께 추출합니다.
- 사용자 답변에 없는 사실을 일반적인 사기 수법만으로 보충하지 않습니다.
- 사용자가 하지 않았다고 부정한 내용, 가정·질문, 일반적인 설명, 사용자와 무관한 타인의 사건은 추출하지 않습니다.
- 모호하거나 서로 충돌하는 내용은 추출하지 않으며, 사용자가 이전 답변을 정정하면 가장 최신 답변을 따릅니다.
- 탐지된 거래와 관계없는 과거 사건의 정황은 추출하지 않습니다.

evidence 규칙:

- evidence는 사용자 답변에 실제로 존재하는 연속된 원문 문자열이어야 하며, 요약하거나 문장을 새로 만들지 않습니다.
- 근거가 여러 문장이나 절에 나뉘면 첫 근거부터 마지막 근거까지를 포함하는 가장 짧은 연속 구간을 그대로 선택합니다. 여러 문장을 포함해도 됩니다.
- 동일한 enum은 한 번만 추출하며, 해당 정황의 필수 조건을 가장 잘 보여주는 evidence를 선택합니다.
- 확인되는 정황이 없으면 fraud_circumstances를 빈 배열로 반환합니다.

#### 추정 금지 규칙을 enum 정의에 위임한 이유

A.3은 정의 블록만 3천 자가 넘고 후보 enum이 20종이라, 전역 규칙 하나가 늘 때마다 모델이
후보마다 교차 검사할 항목이 함께 늘어난다. 아래 5개는 **각 enum 정의 안에 이미 개별 조건으로
들어 있어** 전역 규칙이 같은 말을 반복하는 쪽이었다.

| 뺀 전역 규칙 | 이미 같은 조건을 담고 있는 정의 |
| --- | --- |
| 요청받은 것만으로 실행 추정 금지 | `safe_account_or_asset_inspection_transfer`의 「이체를 요청받기만 했거나 이체하지 않았다고 말하면 추출하지 않음」 |
| 거래 성공 여부만으로 송금·승인 추정 금지 | `own_cash_delivered_to_courier`의 「현금 출금 또는 전달 중 하나만 확인되면 추출하지 않음」 |
| 링크 클릭·앱 설치·인증번호 제공으로 사칭 방식·계정탈취 추정 금지 | `account_reauthentication_phishing`의 「단순히 링크를 받았다는 사실만으로는 추출하지 않음」, `official_call_intercepted`의 「악성앱을 설치했다는 사실만으로 추정하지 않음」 |
| 입금 사실만으로 재송금·출금·전달 추정 금지 | `incoming_funds_forwarded` / `incoming_funds_withdrawn_or_handed_over`의 각 단서 |
| 본인 모르게 거래 발생만으로 탈취 단정 금지 | `hijacked_account_sending_messages`의 「메시지를 받았다는 사실만으로는 추출하지 않음」 등 계정탈취 4종의 단서 |

남긴 상위 2줄(`사용자가 직접 경험했다고 명확하게 말한 정황만 추출합니다`,
`사용자 답변에 없는 내용은 ... 추정하지 않습니다`)이 이 5개가 말하던 원칙 자체다.
**정의를 고칠 때 이 위임 관계를 함께 본다** — enum 정의에서 단서 줄을 지우면 전역 규칙도
없으므로 가드가 통째로 사라진다.

evidence는 여전히 연속된 원문이어야 한다. 다만 한 구절이 정황의 모든 조건을 독립적으로
입증해야 한다는 제한은 두지 않는다. 같은 사건의 근거가 여러 문장에 나뉘면 첫 근거부터 마지막
근거까지의 연속 구간을 사용한다. [extractors.py](../../app/services/chatbot/extractors.py)가 원문에
없는 `evidence`의 정황을 **폐기**하므로 요약하거나 문장을 새로 만드는 것은 허용하지 않는다.

### A.4 대응 가이드 생성 프롬프트

사용처: [2.5 RAG 단계](README.md#rag-단계-가이드-검색-질의별-retrieveaugment-generate는-1회-통합)

가이드 검색 질의 개수와 무관하게 **일반 텍스트 LLM 호출은 1회**다. 중복 제거된 모든 질의를
원래 순서대로 프롬프트에 넣는다. 근거가 있는 위치는 해당 근거만 사용하고, 검색 0건 위치는
[B.5](messages.md#b5-안내를-만들지-못한-가이드-검색-질의-안내) 고정 문구를 정확히 출력한다.
모든 위치가 검색 0건이면 LLM을 호출하지 않고 애플리케이션이 같은 형식으로 조립한다.

**소제목·순서·본문의 최종 조립은 LLM이 소유한다.** 출력은 JSON 객체가 아니라 고객에게
그대로 보여줄 일반 텍스트다. 서버는 비어 있지 않은지만 확인하고 스트림 조각을 누적한다.

`{guide_search_query_context_block}`은 코드가 조립하며 질의 하나가 아래 형식의 한 블록이 된다.

```text
[1]
소제목: 의심스러운 링크 열기
검색 질의: 의심스러운 링크를 연 경우 필요한 대응 방법
고객 발언: 문자로 온 링크를 눌렀어요
근거:
- (출처: 보이스피싱 대응 안내 12p) 청크 내용
- (출처: 보이스피싱 대응 안내 13p) 청크 내용

[2]
소제목: 신분증 사진 전달
검색 질의: 신분증 사진을 보낸 경우 대응 방법
고객 발언: 신분증 사진도 보냈어요
근거:
없음
```

```text
GUIDE_RESPONSE_PROMPT = """
당신은 금융사기가 의심되는 거래의 고객에게 대응 방법을 안내하는 상담 챗봇입니다.

고객 답변에서 분해한 가이드 검색 질의와, 질의별로 검색된 대응 가이드 근거가 아래에 있습니다.

다음 규칙을 따르세요.

- 주어진 위치마다 섹션을 하나씩 작성합니다. 위치를 빠뜨리거나 여러 요구를 합치지 않습니다.
- 입력 위치의 오름차순을 그대로 유지합니다.
- 각 섹션의 첫 줄은 입력에 주어진 소제목을 바꾸지 말고 `■ 소제목` 형식으로 씁니다.
- 소제목 다음 줄부터 그 위치에 붙은 근거에서 확인되는 안내만 작성합니다.
- 다른 위치의 근거나 사전지식으로 답하지 않습니다.
- 근거에 없는 기관명·연락처·금액·기한·절차를 만들어내지 않습니다.
- 근거에 고객이 지금 할 수 있는 조치가 있으면 그 조치를 먼저 안내합니다.
- 피해가 이미 확정되었다고 단정하거나 고객의 책임을 지적하는 표현을 쓰지 않습니다.
- 존댓말로 쓰고 한 요구당 3문장을 넘기지 않습니다.
- `근거: 없음`인 위치의 본문은 다른 말을 만들지 말고 아래 두 줄만 정확히 씁니다.

{ungrounded_message}

- 섹션 사이는 빈 줄 하나로 구분합니다.
- 주어지지 않은 위치를 출력에 추가하지 않습니다.
- JSON, 마크다운 코드 블록, 앞뒤 설명은 출력하지 않습니다. 고객에게 보여줄 섹션 본문만 출력합니다.

가이드 검색 질의와 근거:

{guide_search_query_context_block}
"""
```

모델 호출 실패나 빈 출력은 기존 재시도 횟수를 적용한다. 재시도 직전 빈 스냅샷을 보내 이전
임시 출력을 지우고, 최종 실패하면 서버가 모든 위치를 B.5 문구로 조립한다. 위치별 텍스트
파서는 두지 않으므로 형식 준수는 프롬프트와 골든셋 평가로 관리한다.
